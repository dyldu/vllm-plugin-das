# FP4 default-context memory and live decode work

Omitting `--max-model-len` selects the checkpoint's 1,048,576-token capacity. Before this change, startup with seq64/budget256 reproducibly tried to allocate 39.75 GiB of gather/repack scratch while 23.70 GiB remained free, even though gfx938 executes a direct device copier. Profiling also budgeted 384 decode rows instead of applying the scheduler's 256-token per-pass bound.

Use the same public device predicate during profiling and execution. Reserve the copier's 8 MiB int32 table scratch and an 8.5 GiB persistent ratio-2 pool in this configuration, while preserving conservative gather-fallback accounting. Staging pointers use int64 because this pool exceeds 2 GiB. Decode row capacity derives from min(token budget, request slots times verification rows). No fixed seq, token-budget or context equality gate is added; serving arguments and long-context capacity stay configurable.

Removing the context cap also exposed work that depended on the allocation width rather than live lengths. Stage only live pages using device-length loops; give the native FP4 scorer a fresh device schedule; pass live prefix lengths into exact native ragged TopK; and mask candidate scores only in live columns. Buffers retain static maximum pitches for graph replay. Unwritten tails are never selected. Unsupported selection paths explicitly mask their tails before fallback. Profiling includes both simultaneous logits and rank-mapped score buffers.

The actual 1M-capacity staging probe peaks at 8.5078125 GiB including the 8.5 GiB persistent pool; 8 eager and 16 graph checks exercise offsets beyond 2 GiB, and 2 native scorer byte oracles pass. Three candidate-mask oracles match upstream valid score bytes. At rows48/live4096, native selection takes 33.42 us with a 32K pitch and 32.65 us with a 1M pitch.
